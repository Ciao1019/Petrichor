# 随笔「网页采集」功能设计

状态：以下保留 2026-09-17 的原始设计记录。2026-09-22 已将前端收敛为「收藏原文 / AI 整理」，移除素材收集与高级参数入口；当前行为与启用步骤以 [网页采集实现说明](inbox-web-capture.md) 为准。

## 产品定位

把网页变成可编辑、可追溯、可归档的随笔。用户先选择「想留下什么」，再预览结果、补充自己的想法；抓取参数放在高级选项。

保留当前随笔的三个设计决定：编辑器占满整行；概览和标签索引位于下方列表右侧；编辑器点击后不出现阴影或外圈。

## 入口与主流程

编辑器顶部增加「随手写 / 网页采集」，切换时保留两边的未保存状态。网页采集在同一块全宽区域展开，不新增固定侧栏。

1. 粘贴网址；允许将多个独立网址切换为批量任务。
2. 选择用途，默认「阅读笔记」。展示预估积分和本次输出。
3. 点击「采集并整理」。任务在后台执行，可以继续写随笔。
4. 结果区切换「笔记预览 / 原文 / 网页快照 / 素材」，仅展示实际可用的结果。
5. 勾选要保留的模块、调整标签、补充「我的想法」。
6. 「保存为新随笔」是主操作；「追加到当前草稿」是次操作；保存成功后沿用现有归档流程。

在随手写模式粘贴单独的网址时，提供轻提示「采集这个网页」，不自动替换文字、不自动产生抓取费用。普通行内链接继续保持链接行为。

## 三种用途

按用户反馈，移除「设计灵感」和「结构化资料卡」，不纳入后续分期；用途收敛为阅读笔记、重点摘录、素材收集。

| 用途 | 用户得到什么 | Firecrawl 能力 | Petrichor 需要实现什么 |
| --- | --- | --- | --- |
| 阅读笔记 | 标题、摘要、关键要点、可选全文、来源与自己的想法 | 默认 `markdown` + 用户模型；可选 Firecrawl `json` | 中文整理模板、标签建议、模块选择、编辑与保存 |
| 重点摘录 | 按「我关心的问题」选择原文段落；可另选生成回答 | `highlights`；需要回答时加 `question` | 原文匹配校验、段落定位、引用与回答分开显示 |
| 素材收集 | 图片、参考链接，勾选后存为一个素材随笔 | `images`、`links`、可选 `screenshot` | 去重、预览、选择、图片转存、来源标记 |

首选阅读模板：`summary`、`takeaways[]`、`suggestedTags[]`、`sourceLanguage`、`title`。上述是产品自定义 JSON schema，不是 Firecrawl 固定响应字段。

只有页面存在的信息才能作为事实填入；缺失字段显示「原文未提供」。AI 推断、用户感想和原文摘录使用不同标签，不混写成原文。

## 结果区设计

来源行显示：站点、页面标题、原始链接、采集时间、语言。日期没有证据时不伪造发表时间；原始 URL 与重定向后的 URL 分开保存。

「笔记预览」按模块展示：

- AI 整理：摘要和要点，明确标记生成内容。
- 原文摘录：引用原句，可以回到保存的原文位置。
- 来源附件：完整 Markdown、已转存的截图与选中图片。
- 我的想法：用户自己的编辑区域。
- 标签建议：点选才加入标签，支持继续修改。

预览正文可以进入现有 Plate 编辑器继续编辑。原文快照始终保留，编辑生成笔记不会改写原始快照。外站 HTML 不直接注入产品 DOM；原文默认采用 Markdown 安全渲染。

「保存为新随笔」生成标准随笔卡片，并增加轻量的来源行和「网页采集」标记，不改变普通随笔的主要视觉结构。卡片菜单增加「查看来源」「查看快照」「检查更新」。

「追加到当前草稿」在当前内容后追加一个独立区块，不调用现有会覆盖内容的 `importMarkdown` 方法；需要新增明确的追加方法并提供撤销。新建、预览、失败和模式切换均不清空原来的随笔草稿。

## 让人愿意持续使用的细节

1. **先读重点，再补想法。** 生成笔记保留「我的想法」位置，使采集成为自己的记录。
2. **摘录能回到原文。** `highlights` 的返回文本与本地保存的 Markdown 校验匹配，匹配失败则显示未定位，不能伪造原文行号。
3. **重新采集只看变化。** 使用 `changeTracking` 显示新增、删除、未变化；由用户决定是否把变化保存为新的随笔版本，绝不覆盖用户修改。
4. **批量成功几条就先看几条。** 单条失败独立重试，可以只保存成功结果；默认每个 URL 一条随笔。
5. **同一网页重复收藏有提示。** 在当前用户范围按规范 URL 检查历史，可查看原记录或创建新快照；不强行去掉有意义的查询参数。
6. **知道内容是否完整。** 空内容、疑似登录页、过短正文、上游 warning、截图失败均有明确状态，能保存可用正文。

## Firecrawl 能力与产品映射

以下均根据当前官方说明；服务端应按部署版本维护能力开关。

| 官方能力 | 对应功能 | 范围与注意事项 |
| --- | --- | --- |
| `markdown`、metadata | 整洁正文与来源卡 | 基础采集默认开启；metadata 不保证有作者和日期 |
| `summary` | 快速摘要 | 返回摘要，不等于自动生成中文要点和标签 |
| `json` + prompt/schema | 阅读笔记 | 结构与语言由产品模板规定；按额外积分计算 |
| `question` | 问这个网页 | 返回 `answer`；与原文引用分开 |
| `highlights` | 按主题摘原句 | 返回相关文本；产品负责映射回原文 |
| `screenshot` | 桌面/移动网页快照、长截图 | 可设 `fullPage`、`quality`、`viewport`；链接 24 小时后过期 |
| `images`、`links` | 素材收集与参考链接清单 | 返回 URL，不代表资产已永久保存，也不代表抓完链接内页面 |
| `onlyMainContent`、`includeTags`、`excludeTags` | 正文模式、指定区域、排除杂项 | 正文过滤不需要 LLM；高级选择器不放默认界面 |
| `onlyCleanContent` | 二次净化 | 当前为 Beta、基于 LLM；超长内容可能跳过；能力与费用核验后再开放 |
| JS 渲染、`waitFor`、`actions` | 动态页面增强 | 有界等待/滚动/展开模板；复杂交互官方推荐独立 Interact |
| `location`、`mobile` | 地区语言与移动页面 | 影响网站呈现，不是把原文翻译成中文 |
| `maxAge`、`storeInCache` | 快速复用/重新获取 | 默认缓存窗口 2 天；`maxAge: 0` 请求新抓取；命中缓存仍计费 |
| `changeTracking` | 检查更新与内容差异 | 需要同时请求 Markdown；自动绕过缓存；首轮只建立基线 |
| PDF 等 URL 文档解析 | 在线报告转笔记 | 超长文档可导向现有文档库流程；本地文件 Parse 不是本次 Scrape 范围 |
| `redactPII` | 可选正文脱敏 | 官方说明针对返回 Markdown；不能把截图、其他字段视为已经脱敏 |
| `zeroDataRetention` | 企业特殊配置 | 需要团队开通；与截图不兼容；不等同于仅关闭缓存 |
| `audio`、`video` | 后续媒体资料附件 | 专项文档返回媒体下载地址，约 1 小时有效；不把它宣传成已提供逐字稿 |

Batch Scrape 是 `/batch/scrape`；整站 Crawl、URL 发现 Map、复杂交互 Interact、自动调研 Agent 均是其他端点，不能混作单页 Scrape 参数。首版不自动遍历全站。

## 高级选项

默认折叠，仅提供可理解的设置：

- 内容范围：正文 / 整页；保留图片；保存网页快照。
- 内容新鲜度：优先复用 / 获取最新；结果显示采集时间，不能把缓存结果标为刚更新。
- 动态页面：自动 / 等待更久 / 滚动加载。各模板限制等待、动作数量与页面数。
- 整理语言：原文语言 / 中文。中文转换由 JSON 提取提示词或产品 AI 服务完成。
- 采集地区与页面语言：二级设置，不与整理语言混为一项。
- 指定内容区域：仅在高级选项出现。

不默认暴露 Cookie、任意请求头、可执行脚本、无限滚动或任意浏览器自动化。认证页面需求另行设计凭据与会话生命周期。

## 成本与降级

根据核验当天官方计费文档：

- 普通网页基础 Scrape：1 credit / 页。
- JSON 整理：额外 4 credits / 页，即普通网页阅读笔记预计 5。
- `question` 和 `highlights` 分别额外 4；两者同时开启预计 9，而不是 5。
- 基础变更检测与 git-diff 不额外收费；JSON 变更模式说明为 5 credits / 页。
- PDF 解析按页额外计费；不能把一个长 PDF 当作一张普通网页报价。
- 缓存命中仍计费；高级选项叠加计费；部分特殊站点另有计费规则。
- 403/404 页面若被上游作为 document 返回，仍可能收费；不得写成「失败一律免费」。

界面在开始前显示估算和预计页面数量；实际费用按提供方返回或可确认的用量记录核对，拿不到时显示未确认。管理员可设每日配额、单任务上限、每人并发与批量上限；建议产品首版默认批量最多 10 个 URL、每人并发 2，这些是产品限额而非 Firecrawl 固定上限。

阅读笔记提供「仅保存正文」的低成本路径；AI 整理失败时仍能保留已成功取得的正文。截图失败不使整个网页采集失败。

## 状态与异常

实际持久化任务状态：`queued → scraping → processing → ready`，另有 `partial`、`failed`、`cancelled`；保存状态通过来源关联计算。`processing` 是本地校验、资产转存与结果整理，不伪造 Firecrawl 内部进度。

- 单页显示当前可确认阶段，不显示编造的百分比；批量显示实际完成数。
- 网络超时保留任务标识和所有输入；自动重试需有上限并区分「未发出」和「提供方可能已执行」，避免重复收费。
- Firecrawl API 成功后还要检查 `data.metadata.statusCode` 和内容；2xx/304 才是官方定义的正常页面响应。
- 登录页/验证页/无正文：提示「未取得可用正文」，保留网址，可稍后重试或只记链接；不自动把错误页面保存为文章。
- 402：提示服务配额不足；429：按限流延迟排队，避免连续点击制造更多请求。
- 保存失败：预览和生成内容仍在，可重试幂等保存。
- 关闭预览与取消任务分别处理：关闭不终止后台任务；取消停止后续本地工作，已提交的远端请求可能仍完成并计费。
- 来源超 20,000 字：完整内容作为私有来源快照保留；随笔只保存摘要/选段。明确显示全文字数和随笔长度，不静默截断。

## 接入现有项目

前端沿用 React、现有 Plate、Tabs/Popover/Modal、上传和图标体系，不引入第二套编辑器。新增业务模块建议放在 `apps/web/src/features/pages/inbox/capture/`，拆为输入、模板选择、任务状态、预览与来源附件组件。

Go API 通过服务端 HTTP 客户端调用 Firecrawl v2。项目不需要为接入服务而安装 Firecrawl Node 运行时；后续是否采用官方 Go SDK，以它对目标格式与版本的实际支持决定。密钥、base URL、超时、额度写在服务端配置体系，前端只读取启用状态与可用能力。

调用链：随笔页面 → Gin 鉴权接口 → Asynq 网页采集队列 → Firecrawl → 内容校验/资源转存 → PostgreSQL 任务与来源记录 + S3 快照 → 用户确认后创建随笔。

复用现有 Redis/Asynq worker 与 S3；新增网页队列和独立并发预算，避免占用文档导入与知识构建的全部容量。单页长任务也走后台，浏览器刷新可恢复。批量通过独立 Batch Scrape 适配层接入，完整拉取分页结果并及时持久化，不能依赖其仅保留 24 小时的 API 结果。

接口的实际实现以 [网页采集实现说明](inbox-web-capture.md) 为准；以下保留原始职责规划：

| 接口 | 用途 |
| --- | --- |
| `/api/inbox/capture/create` | 校验 URL/模板/额度，幂等创建任务 |
| `/api/inbox/capture/status` | 当前用户任务及每条 URL 状态 |
| `/api/inbox/capture/result` | 预览与受控附件地址 |
| `/api/inbox/capture/cancel` | 取消尚可取消的处理 |
| `/api/inbox/capture/save` | 事务内创建随笔并关联来源，重复请求返回同一结果 |
| `/api/inbox/capture/check-update` | 创建新快照与比较任务 |

数据职责：

- 采集任务：用户、幂等键、参数摘要、状态、提供方任务 ID、用量、错误码。
- 来源快照：原 URL、最终 URL、标题、实际采集时间、内容哈希、Markdown/截图/资产对象键、生成模板版本、可用格式与 warning。
- 随笔来源关联：一个随笔可以包含多个来源；同一来源的不同快照独立存在，便于批量合并和再次采集。
- `contentMetaJson` 当前承载编辑器/批注元数据，不把任务状态和来源文件硬塞进去；来源用明确的实体与关联。
- 归档时复制来源引用与资产引用，删除随笔后仍被知识库文章引用的快照不得被清理。未保存的临时结果单独配置保留期。

边界保障与抓取本身一起实现：公开 HTTP(S) URL 校验、重定向与资产下载的公网地址校验、大小/类型/超时限制；现有 `research.fetch` 有 URL 校验思路可抽取，但本地校验不等于能限制远端 Firecrawl 的完整网络访问，远端/自托管也要配置相应策略。网页内容只作为数据，不执行其中指令；JSON 输出校验 schema；对象与任务查询都按用户隔离。服务端校验上游返回的分页地址与资产地址，不盲目信任任意 URL。

`changeTracking` 默认按 Firecrawl team + URL 比较；产品还须用稳定、不泄露个人信息的 tag 隔离每位用户/来源的比较历史，并保留本地基线。共用 API key 不能使不同用户看到彼此历史。Webhook 如后续使用，校验原始请求体 HMAC，按事件幂等处理；首版可以使用后台轮询。

## 分期建议

**第一阶段（已实现）：完成可用的采集闭环。** 单网址、阅读笔记、仅正文收藏、重点摘录、截图、来源快照、生成结果编辑、新建/追加、标签、失败恢复、配额与 20,000 字边界。首屏只突出阅读笔记和重点摘录。

**第二阶段（已实现）：完善收集。** 素材收集、批量任务、去重、手动检查更新与 diff。三种用途统一一套预览/保存流程，不再新增另一套操作界面。

**第三阶段（后续独立需求）：持续收集。** 定期检查更新、内容变化提醒、多来源比较。自动调度、通知目标和新增成本需要单独设置；Firecrawl changeTracking 本身只负责单次比较，不是已经开启了后台监控。整站采集更适合接入知识库导入流程。

## 部署与文档差异

本方案以托管 Firecrawl v2 的当前文档为能力上限，自托管只显示实际验证支持的能力。官方明确默认自托管并不覆盖所有 Cloud 能力，截图、页面动作、Interact 等尤其不能承诺开箱即用。

这次核验发现官方页面之间有少量字段差异：格式概览仍提到 `query`，API schema 与专项示例使用 `question` / `highlights`；changeTracking 的 diff 在说明示例中是对象、API schema 中仍写字符串；音视频的计费页文案提到转录，而专项返回示例是媒体 URL。实施应固定服务版本、以真实契约测试归一化响应，不承诺未经验证的字段或转录能力。

本次没有配置密钥、调用收费采集接口或修改数据库。后续实现与上线应验证提供方契约、任务恢复、幂等保存、用户隔离、媒体转存、超长正文、部分失败、桌面/窄屏与明暗主题。
