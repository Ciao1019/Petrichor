# 用对话作为主入口查看和操作系统

## 用户故事

- 作为一个同时管知识库和文档库的人，我希望在一个对话里既能问「有多少个知识库」、也能问某篇资料讲什么，而不是在好几个问答页之间来回切。
- 作为一个要改内容和配置的人，我希望直接说「帮我新建一篇文章 / 打开公开问答」，系统在我权限内去做；碰到删除、批量改、改关键配置时先让我确认，而不是默默改完或什么都不敢动。
- 作为一个已经觉得 Wiki 补丁、分散 QA 入口没用的人，我希望主界面就是对话，旧的问答页和记忆页不再当主入口挡路，而不是再堆一层「更强的知识库问答」。
- 作为一个会连续多轮交代任务的人，我希望它记得我说过的偏好、能把复杂事拆成可见步骤，中途工具失败时能重试或换办法，而不是一轮答完就断片、失败就整段停住。

## 为什么需要

现在站内能力散在知识库问答、文档库问答、记忆页和各种半成品入口里。用户真正想要的不是「把问答再打磨一轮」，而是有一个能查系统、也能办系统里的事的主入口。入口一散，再好的局部优化也像没人用的功能。

## 怎么解决

登录后主界面就是对话。用户用自然语言查资料、问系统状态、改内容、动管理设置；系统按意图接上对应能力，多数操作直接做，危险操作先弹出确认。对话里能看到任务步骤和进度，并带上跨会话记忆；复杂协作与更强的上下文处理可以后补，但不挡「一个入口办事」先成立。原先分散的站内问答入口收掉，对话成为默认主路径；知识库、文档库等原有手动操作界面仍然保留，需要精细操作时照常使用。

## 边界

- 不管给 Cursor / Claude 等外部工具用的 MCP、Skill、API Key 接入——那是另一条产品线，继续独立存在。
- 不取消知识库、文档库等原有操作界面：列表、编辑、上传、设置等手动能力继续保留；对话是主入口和加速器，不是唯一操作面。
- 退役的是分散的站内问答类入口（如独立知识库 QA、文档库 QA、记忆主入口）以及问答链路里的 Wiki 补丁半成品，不是业务 CRUD 页面。
- 不能越权：只能做当前登录用户本来就能做的事；危险操作必须等人确认后才生效。
- 不把「子代理团队、深度上下文压缩」当成第一期有没有的门槛——那是成熟度后续，缺了仍应先能一个入口查事、办事。
- 前提：用户已登录，并已配置好对话所需的模型（以及涉及语义检索时的向量模型）。
